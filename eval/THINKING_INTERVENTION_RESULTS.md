# Thinkingと自動介入の比較（2026-09-16）

**最終判断: 現在の本番を維持。Thinking常時ONと自動介入の追加指示は、今回いずれも採用しない。** 合計160回答・80組のA/Bを評価し、改善例と悪化例、棄却理由を保存した。変更は評価系に限定される。

## 設計と判断方法

[事前計画](FOLLOWUP_THINKING_PLAN.md)に従い、Thinkingと自動介入の指示を別々に比較した。モデルは両方Qwen3 8B / Q4_K_M。プロバイダー内で同じ入力・sampling・出力上限を維持し、候補の変更は一つだけ。推論は直列、Baseline/Candidateの先行順を交互にした。グローバル設定やモデルファイルは変更していない。

過去のアルゴリズムholdoutは既に観測済みのため、今回のtuningへ明示的に移した。別の4問題群・16ケースを新holdoutとして推論前に固定した。Python/JavaScript、正解/バグ/未完成を含み、fixtureを有限領域の独立oracleと照合する。実行根拠はJudgeにのみ渡し、候補モデルには渡さない。

Hard Checkの後、設定名・provider名・速度を隠したランダム順A/BをCodexが読み、9軸と主タスク達成を判定した。同一エージェントが設計も担当しており、完全な独立評価ではない。外部JudgeとA/B順序反転の追試は未実施。言語や反復を独立問題として数えず、問題群単位で95% bootstrap CIを算出した。

「主タスク達成」は正しい内容に加え、依頼の範囲とヒント制約を満たすこと。キーワード/API名の提案は許容し、完成した置換式の提示は不合格とする。自動介入では正解コードへの沈黙と、誤りへの適切なヒントを両方評価する。

## T: Thinkingのみ変更

4ケース×OFF/ON×2provider = 16回答のpilot。これは実用性の確認であり、精度優越を確定する規模ではない。

| Provider | 主タスク達成 OFF→ON | 待ち時間中央値 OFF→ON | ONのタイムアウト | tie=0.5の勝率 / 問題群CI |
|---|---:|---:|---:|---|
| LM Studio | 1/4→2/4 | 6.65→43.23秒（6.50倍） | 1/4 | 62.5% / 0–100% |
| Ollama | 2/4→2/4 | 10.62→37.40秒（3.52倍） | 0/4 | 62.5% / 50–100% |

両方とも事前のpilot拡大条件「中央値3倍以内」を満たさず、**常時ON候補は棄却、追加の全面評価には進めない**。出力上限到達は0件で、上限増加の診断条件にも該当しなかった。LM Studioは完了3件、Ollamaは4件で実際のreasoning出力のカウンターを確認した。タイムアウトした1件のreasoning量は不明。

具体例:

- LM Studioのlower-bound Python: OFFは重複時の説明をleftの右移動に誤って帰属。ONは結果1に加え、等値時にrightをmiddleへ絞る動作を正しく説明した。
- LM Studioの総和バグ: OFFにあった誤った範囲外アクセスの診断がONで消えた。ただし両方が完成したループ条件を提示し、ヒント制約は未達。
- Ollamaのtwo-pointer: ONは8→9→11と実際の例を追えたが、ループ終了の説明に誤りが残った。OFFは例の最初に通る分岐を説明せず修正を開示。ONでも主タスク達成とは判定しない。
- 正しい総和コードへの自動介入は、両provider・両モードとも沈黙できた。この1例から全般的な抑制効果は推定しない。

LMのend-to-end correctnessは+0.50、instruction followingは-1.00（タイムアウトを全軸0として含む）。Ollamaはcorrectness ±0、instruction following +0.75、conciseness -0.50。全9軸とtransport障害を除いた意味評価は各[LMレポート](results/af-lm-thinking-comparison/report.md)・[Ollamaレポート](results/af-oll-thinking-comparison/report.md)に保存。

LM Studioの出力上限は2048、Ollamaは8192で、それぞれ現在の本番値を保持。実測contextはLM 8192、Ollama 4096（モデルmetadataの最大40960と区別）。同じQ4_K_Mでもテンプレート・backend設定・上限が異なるため、provider間の差をThinkingの能力差とは扱わない。samplingの未指定値はbackend継承であり、値が不明ならnullのまま保存した。Ollamaの最初のOFFにはロード時間を含む可能性があるが、本番OpenAI互換APIでは分離できず、decode tokens/secも推定で補っていない。

Ollamaの取得済みモデル既定値はtemperature 0.6 / top_p 0.95 / top_k 20 / repeat_penalty 1。公式Non-Thinking候補の0.7 / 0.8とは異なるが、今回はThinkingだけを比較するため両armで保持した。min_pは不明。公式sampling候補は既存configsに残っており、この結果を公式最適設定での能力限界とは解釈しない。

## A: 不要な自動介入の抑制

ThinkingはOFFのまま。「具体的な入力/条件・現状の動作・未充足の要件を確認してからヒントを出す」という一般指示のみを追加。正しいコードへの確認要求・賞賛・満たされた仕様の言い換えは発話理由にしない。一方、実証された不具合や未完成は沈黙で隠さない。アルゴリズム名やfixture固有の正解を指示に埋め込んでいない。

14ケース×2反復×Baseline/Candidate×2provider = 112回答。正解6ケース、不具合/未完成8ケース。各armで正解12観測、不具合/未完成16観測。問題群は5つ。

### LM Studio: 調整用データ

主タスク達成9/28→11/28。不要な介入8/12→7/12。不具合への沈黙5/16→4/16、不具合/未完成での主タスク達成5/16→6/16。10勝14分4敗、tie調整勝率60.7%、問題群均等60.0%、95% CI 52.5–67.5%。中央値7.39→7.64秒（+3.5%）。全9軸の平均に悪化はない。

ただし、改善の多くは「誤答が弱まった」であり完全な解決ではない。正しい累積和への沈黙が1観測増え、Python sortの文字列キーへの適切なヒントも得られた一方、JavaScript BFSでは正しい終了条件を壊す置換式を新たに提示した。Python sortの別反復では適切なヒントが完成引数の提示へ悪化した。個別の悪化を総合点で隠さない。

調整用の数値条件は通過したため、[選択時点の記録](results/af-lm-selection.json)を固定し、新holdoutを1回だけ実行する。**この時点では本番未採用**。[全回答と9軸](results/af-lm-automatic-comparison/report.md)。

### Ollama: 調整用データで棄却

主タスク達成11/28→11/28。不要な介入6/12→5/12と減る一方、不具合への沈黙6/16→7/16、不具合/未完成の主タスク達成5/16→4/16に悪化。4勝21分3敗、tie調整勝率51.8%、問題群均等52.5%、95% CI 50.0–57.5%。中央値5.65→5.42秒。correctness +0.11、instruction following ±0など、平均軸は悪化しないが、階段数Pythonで新しい沈黙、sort Pythonでヒントから完成引数への悪化がある。

**見逃しが増えるため棄却**。不要な助言の減少だけでは採用しない。[全回答と9軸](results/af-oll-automatic-comparison/report.md)。Ollamaでは新holdoutへの追加推論を行わない。

### LM Studio: 新holdoutで確認し棄却

固定した4問題群・16ケースを両armで1回ずつ取得（32回答）。候補の再調整なし。主タスク達成8/16→8/16、不要な介入2/4→2/4、バグへの沈黙4/8→4/8。4勝7分5敗、勝率46.9%、問題群95% CI 25.0–62.5%。中央値7.52→6.16秒、p95は11.94→15.72秒。Hard passは両方10/16だが、**merge-bug-jsで新たな沈黙が発生**し、ケース単位の「新しいHard Check失敗なし」を満たさない。

GCD JavaScriptのバグでは、入力順という誤った原因から、終了時b=0とreturn bの矛盾へ改善した。一方、全負配列で失敗する最大部分配列を正しいと保証し、正しい括弧判定には仕様にない波括弧の処理を求める例が残った。correctness平均+0.31、instruction following +0.19でも、不要な介入の減少は再現せず、conciseness -0.06。平均点だけで採用しない。

このholdoutには、自動ポリシーを適用しない手動質問4ケースも含む。自動12ケースの主タスク達成は4→5、**同一リクエストの手動対照は4→3**。手動側の回答差は生成の変動であり、追加ポリシーの因果効果とは扱わない。上記16件全体の速度差や勝率も、この対照を含む点に注意する。

**新規Hard Check失敗と、不要な介入抑制の再現不足により棄却。** [全回答と9軸](results/af-lm-confirmation-comparison/report.md)。新holdoutは観測済みとなったため、次の最適化で未見データとして再利用しない。

## 現在のChampionと次の仮説

現在の本番（既存のコンテキスト保持・限定した数値参照、Thinking OFF）を維持。今回の候補プロンプトはeval内だけに残し、本番のLM Studio/Ollama/Copilot経路には適用しない。モデル削除、量子化変更、グローバル設定変更もなし。

今回分かったボトルネックは、短いコードでも境界条件・変数の終了状態・戻り値と画面出力の契約を誤読すること、正しいコードを認識しても確認要求を出すこと、ヒントと完成した修正の境界を守れないこと。取得済みコードが欠ける問題とは分けて考える。これはQwen3 8Bの能力上限を確定する証拠ではない。Thinkingは一部の推論を改善したが、本番時間制限との相性が悪かった。

次の検証候補（今回未実施）:

1. 手動の難しい質問に限るThinkingの明示選択。待ち時間を許容する用途を分け、120秒以内に終わる割合と説明の正確さを新問題群で確認する。常時ONにはしない。
2. 自動介入の判定とヒント生成を分け、先に「具体的な反例・未充足要件」を確認する候補。正解への誤警告とバグの見逃しを同時に測り、二段階化の速度負担も比較する。「何も言わなければ合格」にはしない。
3. レビュー済み評価fixtureの実行根拠を与えた診断との対照実験。根拠があれば改善するのか、根拠を渡しても推論/指示遵守を誤るのかを切り分ける。ユーザーコードの本番自動実行を追加する提案ではない。

小さい差にはJudge依存性があるため、次の本番採用候補は独立Judgeまたは順序反転で追認する。今回は失敗を確認した候補を繰り返し微調整せず、この2種類の比較を終了する。

## 実装・検証

- `run-paired.mjs`: 交互の先行順、各回答のcheckpoint、同条件での中断再開。完了した回答や失敗を再取得で置き換えない。
- `paired-diagnostics.mjs`: Thinkingまたは自動指示以外に変更がないこと、同じ入力であることを実データで検査。
- `followup-report.mjs`: 明示した手動判定から採否条件を再計算し、固定holdoutのハッシュを確認。自動採用はしない。
- 新しい独立問題群と有限領域oracle、9軸の匿名手動評価、全160回答の記録を追加。
- `npm run test:quality-eval`: 16件成功（拡張コンパイルを含む）。`npm run lint`成功。新スクリプトの構文検査、実データの集計、入力保持確認、ローカル個人パスの検査を実施。

集計: [af-summary.json](results/af-summary.json)、採否: [af-decisions.json](results/af-decisions.json)、横断的な実験台帳: [experiments.json](results/experiments.json)。各runにtoken数・tokens/sec（取得できる場合）・model/quantization・context・sampling・出力上限・source hash・失敗分類を保存。
