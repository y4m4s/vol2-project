# アルゴリズム問題の評価結果 — 2026-09-16

## 結論

Python / JavaScriptのアルゴリズム問題を対象に、実行根拠付きの評価セットを追加し、**176回答**を測定した。問題文の見出し追加だけでは明確な改善を確認できず、**本番のprompt・推論設定は変更していない**。現在のChampionは既存の設定を維持するという意味であり、アルゴリズム用途の品質を保証する認定ではない。

大きな課題は、コードが短く全文が届いていても、探索方向・初期値・区間端を誤って説明することと、正解済みのコードにも自動で介入することだった。

## 追加した評価基盤

- tuning: 6問題群・8変種 × 2言語 = 16ケース、各3反復。
- holdout: tuningと異なる4問題群・8変種 × 2言語 = 16ケース、各providerで1回。候補棄却・設定固定後に実行し、その回答で追加調整していない。
- tuningは総和の正解／バグ／未完成、二分探索、頻度集計、2ポインタ、計算量、情報不足。holdoutは区間和・最短距離・階段の数え上げ・数値ソート。
- レビュー済みfixtureをPython / Nodeで実行し、独立した単純な参照実装と照合。合計19,392入力検査。両言語の合否が一致し、正解fixtureには検査範囲内の不一致なし、バグfixtureには反例あり。
- 実行根拠・反例はJudgeにだけ渡す。候補モデルが受け取るのは問題文・制約・例・編集コード・質問。
- 既存の9軸・Hard Check・匿名A/Bに加え、言語・問題・変種別集計、問題単位bootstrap、評価基準のrunごとの保存、実行環境versionとhashの記録を追加。
- API/キーワード名のヒントは許容する。`shift`という名前は許容し、完成した更新式・比較関数・置換引数の提示はヒントのみの依頼では減点する。

設計と再実行手順: [ALGORITHMS.md](ALGORITHMS.md)。再集計可能な結果: [alg-summary.json](results/alg-summary.json)。全設定: [experiments.json](results/experiments.json)。

## 現行設定のBaseline

「主要要件を満たす」は、回答をコード・条件・実行根拠と照合したCodexの判定。軽微な表現の弱さは許容するが、誤診・核心の説明不足・完成式の開示・不要な自動介入は不合格とした。Hard Checkの合格率とは別の指標で、一般的な正答率の保証ではない。

| tuning | Hard Check | 主要要件を満たす | Python | JavaScript | 応答中央値 / p95 |
|---|---:|---:|---:|---:|---:|
| LM Studio 現行 | 48/48 | 30/48 | 15/24 | 15/24 | 8.48 / 13.88秒 |
| Ollama 現行 | 48/48 | 33/48 | 16/24 | 17/24 | 7.36 / 18.47秒 |

両providerとも総和の正解での不要な発話は0/6、バグ・未完成での沈黙は0/12。しかし、形式が正しくバグに反応していても、説明やヒントの範囲が適切とは限らない。

### 実際の失敗

- **探索方向の誤答**: lower_boundの戻り値1は合っていても、等値時の`right = middle`を説明せず、`left`を右へ進めるから最初の位置が見つかると説明。
- **存在しない原因**: `[1,2,4,7]`の2ポインタ問題を「重複する値のため見逃す」と説明。実際の問題は移動すると和が目標から遠ざかること。
- **計算の誤り**: N=200,000の二重ループを約4億件と説明したLM回答があった。実際の組数は19,999,900,000。
- **誤った修正案**: Ollamaが空のPython辞書に`counts[ch] += 1`、JavaScriptに未初期化の`counts[ch] + 1`を提案。初回にKeyError / NaNになる。
- **ヒントの出し過ぎ**: 頻度集計や末尾欠落に、更新式や変更後のループ条件を提示。tuningでLM 6/48、Ollama 8/48。

コード推論エラーはLM 11/48、Ollama 9/48。これは単独レビューの失敗分類で、provider優劣の統計的な証明ではない。

## Holdout: 別問題への適用

| 現行設定 | Hard Check | 主要要件を満たす | Python / JavaScript | 正解済みへの不要な発話 | 欠陥があるのに沈黙 | 中央値 / p95 |
|---|---:|---:|---:|---:|---:|---:|
| LM Studio | 10/16 | 6/16 | 2/8・4/8 | 4/6 | 2/6 | 8.01 / 12.66秒 |
| Ollama | 11/16 | 6/16 | 2/8・4/8 | 3/6 | 2/6 | 6.91 / 9.69秒 |

不要な発話には誤指摘だけでなく「要件を満たすので確認して」という不要な確認依頼も含む。欠陥で発話していても別の原因を指摘する回答は、この沈黙数には含まれず、意味評価で別途不合格になる。

- 正しいBFSに、LMは「有向グラフを考慮していない」、Ollamaは「距離を保持していない」と誤指摘。
- JavaScriptの区間和・階段初期値のバグでは、両providerが沈黙。
- Pythonの階段バグについて、LMは`range(2,n+1)`で2が実行されないと誤答。本当は0段の初期値が原因。
- 一方、階段の正しい実装の結果5や、JavaScriptのLIFO/FIFOへの着目は両providerで説明できた。

詳細: [LM assessment](results/alg-lm-holdout/assessment.json)、[Ollama assessment](results/alg-oll-holdout/assessment.json)。tuningとは問題が異なるため、数値差を設定変更による悪化と解釈しない。次の最適化でこのholdoutを未使用データとして扱わない。

samplingは現行経路からの未指定値を継承し、新しい数値を設定していない。Ollamaの登録済みdefaultsや取得できたメタデータはenvironment-before/afterと実験台帳に保存。未取得の設定値は推測で埋めていない。

全176回答で送信前のコードと問題文が保持されていることを確認。短い入力であり、今回はアプリ側の切り詰めより推論・知識・指示追従の検証を優先すべき結果だった。ただし、backendの処理token数だけで完全な無切捨てを証明するものではない。context量の候補を比較していないため、今回からcontext長のPareto frontierや最適値は主張しない。

provider間はtemplate・既定値・出力枠・アプリのdepth処理も異なる。同じ8B/Q4というだけで重みや実行条件が等しいと仮定せず、品質差をバックエンド固有の優劣に帰属させない。

## 評価の修正と限界

初回LMのHard Checkはバグへの`review`も誤って落としていた。具体的な編集済み欠陥は`continue`/`review`の両方を許容するよう**評価メタデータだけ**を修正した。元の[alg-lm-baseline](results/alg-lm-baseline/manifest.json)を保持し、入力・送信prompt・runtime判定が不変であることを検証して[alg-lm-baseline-v2](results/alg-lm-baseline-v2/manifest.json)へ再採点。48件の新規生成としては数えていない。同じ条件を候補と、回答未取得のholdoutへ適用した。

回答取得後の最終点検では、数値Hard Checkが`1,000`等の先頭だけを1と認定しないよう境界判定を強化した。全176回答の送信内容・runtime判定・Hard Checkが変わらないことを`node eval/verify-algorithm-results.mjs`で検証し、[alg-verification.json](results/alg-verification.json)に記録。モデル入力や意味評価の追加最適化はない。

- 同じCodexが問題設計と採点を担当。A/Bキーを判定後に開示したがBaselineを先に閲覧しており、完全な匿名性や独立Judge評価ではない。外部API Judgeは既存adapterで交換可能。
- ケースはオリジナルの小さい関数（最大393文字）。入力パース、複数ファイル、長い競技コード、木・複雑なDP、TypeScriptの型チェックは未評価。有限領域の実行成功は全制約での証明ではない。
- 実行するのはレビュー済みfixtureのみ。任意のユーザーコードやモデル生成コードを安全に実行するsandboxではない。
- 同一問題の言語違い・変種・反復は独立問題ではない。holdoutは4問題群・1反復で、不確実性が大きい。
- Copilot/OrcaRouterの比較回答は今回取得していない。ローカルとの差の大きさやモデル能力の絶対的限界は未判定。

## 次に検証すべき仮説

1. **不要な自動介入の抑制**: 正しいコードへの確認要求と、実際の不一致へのヒントを区別する汎用的な判定方針。今回のholdoutに直接合わせず、新しい問題群で検証する。
2. **短いコードの推論精度**: Thinkingの切替で探索・初期値の説明が改善するかを、次の独立した変数として試す。速度・出力長と併せて判断する。
3. **誤った修正案と解答開示**: API名だけのヒントを保ちながら、不正な更新式を勧めないかを新しい例で確認する。今回の誤答を列挙した暗記用promptは作らない。

今回は評価対象の再構成と最小候補1ラウンドを完了した。見出し追加で埋まらない差はあるが、Thinking・モデル比較を制御していないため「8Bの能力限界」とは断定しない。
